# 用 React Native 做一个免费开源无广告的音乐播放器

同一首歌可能来自本地文件，也可能来自一个远程 URL。对播放器来说，最终都是播放音频，但它们的导入、地址解析和离线处理并不相同。

如果把这些差异都写进播放控制逻辑，每增加一种来源，就要重新检查队列、切歌和缓存之间的关系。

**轻松音乐 EasyMusic** 在这里做了一个明确的拆分：来源模块负责找到可播放资源，播放模块负责控制播放。它是一个免费、开源、无广告的个人音乐播放器，使用 React Native、Expo 和 TypeScript 开发，源码在 [GitHub](https://github.com/colinli007/easy-music)。

## 先统一播放需要的输入

本地文件与远程地址的差异，应尽量留在来源层。

项目将来源解析结果统一为可播放地址及必要的请求信息。播放模块通过 `src/sources/resolve.ts` 获取这些信息，不直接处理具体来源的实现。

对使用者来说，这意味着自己导入的本地音乐和远程音频可以进入同一套曲库、歌单与播放流程。对开发者来说，来源变动更容易限制在来源模块内部。

这条边界也有一个务实的例外：导入流程本来就需要知道来源类型。本地导入要打开文件选择器，远程导入要处理 URL，所以项目没有要求所有模块都对来源一无所知。

## 离线缓存放在统一解析入口

离线播放有一个很适合提前决定的问题：既然本地已经有可用文件，还要不要先请求远程来源？

轻松音乐的处理顺序是：

1. 接到曲目解析请求，先检查有效的本地缓存。
2. 命中缓存，直接返回本地文件地址。
3. 没有有效缓存，再调用曲目对应的来源解析。

这样，播放层拿到的仍然是统一的解析结果，不需要额外维护一套离线播放分支。缓存文件仍然有效时，播放也不必依赖原来的远程来源再次响应。

这不等于保证任意远程歌曲都能下载。下载前仍需要来源提供有效内容；缓存的职责是复用已经成功保存的文件。

## 插件能力留在门面之后

Android 与 iOS 都支持用户自行安装插件，但核心播放能力不依赖插件实现。插件模块只通过一个门面对外，核心代码看不到插件内部。

这让本地播放、远程 URL、曲库与歌单等核心能力可以与插件系统分开维护。插件能力也因此有明确边界：不装任何插件，应用仍是完整的播放器；装了插件能做什么，取决于具体插件。

应用不内置音乐资源或插件源，插件也没有沙箱。这里的可扩展性依赖用户自行选择可信来源。

## 除了架构也有日常播放能力

轻松音乐已经实现了本地音乐与远程 URL 导入、歌单、后台播放和锁屏控制、歌词、手动离线缓存、最近播放，以及 M3U 播放列表导入。

如果你正在做类似项目，可以从三个位置开始读代码：

- [`src/sources/resolve.ts`](https://github.com/colinli007/easy-music/blob/main/src/sources/resolve.ts)：统一解析与缓存优先顺序。
- [`src/playback/player.ts`](https://github.com/colinli007/easy-music/blob/main/src/playback/player.ts)：播放控制与系统媒体能力。
- [`docs/architecture.md`](https://github.com/colinli007/easy-music/blob/main/docs/architecture.md)：分层职责、依赖方向和相关取舍。

源码可以帮助理解实现方式；各平台的可用版本与验证状态，请以仓库的版本说明为准。
